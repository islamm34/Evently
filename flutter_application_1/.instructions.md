# Flutter Architecture, State Management & Project Structure

The application must follow a **professional enterprise-level Flutter architecture**.

The generated code should be scalable, maintainable, testable, and production-ready.

---

# State Management

Use:

## Riverpod (Required)

Latest stable version.

The entire application must rely on Riverpod for state management.

Use:

- Provider
- StateProvider
- FutureProvider
- StreamProvider
- AsyncNotifierProvider
- NotifierProvider

when appropriate.

Avoid:

- setState for business logic
- Global variables
- Unstructured state management

State management should handle:

- Authentication
- User Role
- Queues
- Tickets
- Businesses
- Notifications
- Analytics
- Theme
- Settings

---

# Dependency Injection

Use Riverpod as Dependency Injection.

Inject:

- Repositories
- Services
- Data Sources
- Dio Client
- Supabase Client
- Notification Services

through providers.

# Strict Separation of Layers

## Presentation Layer

Responsible for:

- UI
- Widgets
- Animations
- User interactions

Must NOT contain:

- API calls
- Business logic
- Data processing

---

## Domain Layer

Responsible for:

- Business rules
- Use Cases
- Entities
- Repository Contracts

This layer must be independent of Flutter.

---

## Data Layer

Responsible for:

- API communication
- Local storage
- Repository implementation
- DTOs and Models

---

# Dio Networking Architecture

Use Dio for all API requests.

Create:

```
core/network/

├── dio_client.dart
├── api_endpoints.dart
├── interceptors/
│   ├── auth_interceptor.dart
│   ├── logging_interceptor.dart
│   └── error_interceptor.dart
```

Requirements:

- Centralized API layer
- Request logging
- Error handling
- Token refresh support
- Retry mechanism

---

# Repository Pattern

Implement repository pattern.

Example:

```
domain/repositories/

abstract class QueueRepository

data/repositories/

class QueueRepositoryImpl
```

The UI must never directly access APIs.
